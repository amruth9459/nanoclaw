# ADK Identity & Trust Gap Analysis — and NanoClaw Enhancements

**Source material:** Google Developers Blog — "Building Pausable & Resumable Agents with ADK"
**Companion docs:** `GOOGLE_ADK_ANALYSIS.md` (workflow-state focus), `AGENT_IDENTITY_TRUST_ARCHITECTURE.md` (NanoClaw design)

---

## Executive Summary

- Google ADK solves *workflow state durability* well — externalized step pointer, atomic state-delta merges, native pause/resume — but treats *identity* as an implicit framework boundary. Six structural identity gaps remain.
- NanoClaw's existing `src/identity/` layer (Ed25519 keypairs, hash-linked `EvidenceRecord` chain, scoped `AgentScope` enum, `AgentTrustScore`) already closes three of the six gaps ADK leaves open: cryptographic sub-agent identity, signed audit trail, and basic credential expiry.
- The remaining three gaps (webhook caller verification, per-key state-transition authorization, credential rotation/revocation) are addressable with focused additions that compose with existing types — no rewrite required.
- Two of the proposed enhancements (signed webhook resume, scoped state-key ACL) are prerequisites for safely shipping the `workflow_state` machine proposed in `IDENTITY_GRAPH_PROPOSAL.md`. They should land in the same window.

## 1. ADK Architecture Overview (identity-relevant slice)

The ADK programming model centers on three primitives. Each has an identity/trust seam.

| Primitive | Purpose | Identity touch-point |
|---|---|---|
| `SessionService` (SQLite/CloudSQL) | Durable per-session state | Sessions identified by `(user_id, session_id)` string pair — no signature, no key |
| `tool_context.state["key"] = value` | Atomic state writes that merge into `state_delta` | Caller of the tool is the framework runtime — no record of *which* sub-agent wrote which key |
| `Agent(sub_agents=["it_agent", ...])` | Sub-agent delegation | Sub-agent referenced by string name; framework instantiates from registry — no identity material exchanged |

Resume is webhook-driven: an external service POSTs `{user_id, session_id, state_delta}` to a callback like `receive_signed_documents_callback`. The framework looks up the session by ID, merges the delta, re-enters the state machine at the persisted step.

The "signed" in `receive_signed_documents_callback` refers to documents the *external service* received from a signing vendor — **not** to any signature on the webhook payload itself.

## 2. Identity & Trust Gap Analysis

### Gap 1 — No webhook caller verification

**ADK pattern (paraphrased):**
```python
@app.post("/callback/documents-signed")
async def receive_signed_documents_callback(user_id: str, session_id: str, payload: dict):
    session = session_service.get(user_id, session_id)
    # state_delta merged unconditionally
    session.state.update(payload["state_delta"])
    return await runner.run_async(session)
```

Anyone with the URL + a guessable or leaked `session_id` can resume the workflow with attacker-controlled `state_delta`. There is no signature check, no HMAC, no caller authentication. The framework treats *possession of a session_id* as proof of authorization to advance state.

**Why this is structural, not a bug:** ADK's session ID is a UUID generated by the framework. It is never given a confidentiality classification, but in practice it appears in logs, dashboards, and may pass through unencrypted webhook configurations. There is no rotation mechanism if a session ID leaks mid-workflow.

**Failure mode:** A workflow paused waiting for a Stripe webhook can be resumed by any party that obtains the session_id, with arbitrary payment-confirmation state — bypassing the real payment.

---

### Gap 2 — Flat state ownership; no per-key RBAC

**ADK pattern:**
```python
class SalesAgent(Agent):
    async def run(self, tool_context):
        tool_context.state["deal.amount"] = 50000
        tool_context.state["customer.credit_check"] = "passed"   # not its concern
        tool_context.state["finance.approved"] = True            # definitely not its concern
```

All keys live in one flat dict. Any sub-agent with a tool call can write any key. There is no notion of "the sales agent owns `deal.*`, finance agent owns `finance.*`." Cross-agent state forgery is trivial inside a multi-agent system.

**Why this is structural:** The `state_delta` merge in `SessionService` is a dict-update operation. It has no knowledge of which agent issued the delta, because by the time the framework merges it the delta is just a JSON blob.

**Failure mode:** A compromised or hallucinating sub-agent can write `finance.approved = True` and the parent agent — reading state per the ADK doctrine — sees that as ground truth on the next turn.

---

### Gap 3 — Sub-agents identified by strings; no capability verification

**ADK pattern:**
```python
agent = Agent(
    name="customer_onboarding",
    sub_agents=["it_agent", "finance_agent", "hr_agent"],
)
```

`sub_agents` is a list of strings. The framework resolves them at runtime from a class registry. There is no cryptographic identity for sub-agents, no per-sub-agent scope list, no way to verify "the `finance_agent` that just wrote `finance.approved=True` is the same `finance_agent` the orchestrator was configured with."

**Failure mode:** If the registry is mutable or the agent loading path is influenced by configuration, an attacker can substitute a malicious `finance_agent` class. The orchestrator has no way to detect the swap.

---

### Gap 4 — No state transition authorization

**ADK pattern:**
```python
# Any tool call inside any sub-agent
tool_context.state["workflow_step"] = "shipping"
```

State transitions are unauthorized writes. The framework persists the delta atomically — that is the *concurrency* guarantee. There is no *authorization* check: nothing validates that the writing agent is permitted to advance to `shipping`, or to bypass `payment_pending`.

**Failure mode:** A model hallucination that writes `workflow_step = "completed"` succeeds. The state machine's "current step" is whatever the last write said it was, and the agent on the next turn reads that step as authoritative.

---

### Gap 5 — No audit trail of who modified state when

**ADK pattern:**
The `SessionService` persists the current `state` blob. It does not persist a log of *who wrote which key when with what tool*. The article describes resume semantics, not forensic semantics. If a customer dispute requires "show me what the agent saw when it approved this," ADK gives you the final state, not the chain of events that produced it.

**Failure mode:** Post-incident investigation cannot distinguish "the sales agent legitimately set `discount = 30%`" from "the discount agent forged a delta during the doc-signing pause."

---

### Gap 6 — No credential lifecycle management

ADK has no credentials to manage. Sub-agents are class instances; their authority is implicit in their position in the agent tree. There is therefore:
- No expiry — an agent can "act" for the lifetime of the process.
- No revocation — a misbehaving sub-agent type must be removed in code and redeployed.
- No rotation — there is nothing to rotate.

ADK relies on the deployment boundary to manage trust. This is fine for monolithic deployments but breaks down for cross-org multi-agent systems where one party's sub-agent runs inside another party's orchestrator.

## 3. NanoClaw Comparison

| Gap | ADK status | NanoClaw status (today) |
|---|---|---|
| 1. Webhook caller verification | Absent | Partial — no `webhook_resume` surface exists yet. Inter-agent `SignedMessage` uses Ed25519 + nonce, so the *pattern* is established. |
| 2. Per-key state RBAC | Absent | Absent — but `AgentScope` enum exists; no state machine writes scopes today, so the gap is *hypothetical* until `workflow_state` lands. |
| 3. Sub-agent cryptographic identity | Absent | Closed — `createIdentity()` mints an Ed25519 keypair per spawned agent; messages signed via `signMessage()`; verified via `verifyMessage()` with replay-protected `nonce`. |
| 4. State transition authorization | Absent | Absent — `workflow_transition` design in `IDENTITY_GRAPH_PROPOSAL.md` has optimistic concurrency but no scope check. |
| 5. Audit trail | Absent | Closed — `EvidenceRecord` is hash-chained (`prev_record_hash` → `record_hash`) and Ed25519-signed by the acting agent. `verifyChain()` detects tampering. |
| 6. Credential lifecycle | Absent | Partial — `AgentIdentity.expires_at` enforced at verification; `expireIdentity()` flips status. No rotation primitive, no revocation list, no compromise-response flow. |

**Net:** Three gaps closed (3, 5, partial 1+6), three open (1 for webhooks, 2, 4, 6 rotation).

The two truly open structural gaps — **2 (per-key state ACL)** and **4 (transition authorization)** — only matter once the proposed `workflow_state` machine ships. They are blockers, not optional polish: shipping `workflow_transition` without per-key authorization would import ADK's gap into NanoClaw and waste the identity layer we already built.

## 4. Proposed Enhancements

### Enhancement 1: Signed Webhook Resume

**Problem:** Gap 1 — once `src/channels/webhook.ts` ships (per `IDENTITY_GRAPH_PROPOSAL.md` §3.5), anyone with a leaked `continuation_token` can resume a paused workflow with attacker-controlled `state_delta`. The proposed HMAC mitigates spoofing of *known* external services but does not bind the resume to a verified identity.

**ADK pattern:** Webhook posts `{user_id, session_id, payload}`. Framework merges payload into `state` and runs. No signature on the webhook itself.

**Proposed solution:** Treat every webhook resume as an inbound `SignedMessage` of type `workflow_resume`. The external system pre-registers an Ed25519 public key (or uses an existing NanoClaw `AgentIdentity` for trusted partners). The webhook body MUST carry a signature over `(continuation_token, state_delta, timestamp, nonce)`. The resume handler verifies via the same `verifyMessage()` path used for inter-agent messages, with the same nonce-replay protection.

**Implementation sketch:**
```typescript
// src/channels/webhook.ts
import { verifyMessage } from '../identity/index.js';
import { resumeWorkflow } from '../workflow-state.js';

app.post('/webhook/workflow/resume', async (req, res) => {
  const { continuation_token, state_delta, signature, public_key, nonce, timestamp } = req.body;

  // Build an UnsignedMessage-shaped envelope from the webhook fields.
  const envelope = {
    type: 'workflow_resume' as const,         // requires extending SignedMessageType
    sender_agent_id: req.body.sender_agent_id, // pre-registered partner id
    content: JSON.stringify({ continuation_token, state_delta }),
    summary: `resume ${continuation_token}`,
    timestamp,
    nonce,
    signature,
    public_key,
  };

  const verification = await verifyMessage(envelope, {
    requiredScope: 'workflow.resume',  // new scope
    maxAgeSeconds: 300,                // tighter than message default
  });

  if (!verification.authorized) {
    return res.status(401).json({ error: 'unauthorized', checks: verification.checks });
  }

  const result = await resumeWorkflow(continuation_token, state_delta, envelope.sender_agent_id);
  res.status(result.success ? 202 : 409).json(result);
});
```

**Security properties:**
- Webhook payload signed end-to-end (not just transport-layer TLS).
- Replay-protected via `nonce` table reuse from `message-signing.ts`.
- Resume action attributed to a specific `sender_agent_id` — auditable.
- Sender's scope must include `workflow.resume` — denies otherwise-valid signatures from agents lacking that scope.

**Trade-offs:**
- External partners must hold a NanoClaw-issued or NanoClaw-registered Ed25519 keypair. This is friction for one-off Stripe/Twilio integrations, which is why we keep HMAC as an opt-in fallback path for low-trust resume sources (low-trust resumes pause for HITL before running).
- Time-skew between external systems and the NanoClaw host must stay under `maxAgeSeconds`. NTP assumed.

### Enhancement 2: Scope-Tagged State Keys (per-key write ACL)

**Problem:** Gap 2 + Gap 4 — when the proposed `workflow_state.state_blob` lands, any agent with a `workflow_transition` IPC will be able to write any key. This re-imports ADK's flat-state problem.

**ADK pattern:** Flat `state` dict; any tool writes any key.

**Proposed solution:** Two-part change to `workflow_state.ts`:

1. **Schema-declared key ownership.** Each `workflow_type` registers an ACL table at boot:
   ```typescript
   const workflowKeyAcls: Record<string, Record<string, AgentScope[]>> = {
     'doc_signing_workflow': {
       'docs.requested':   ['agent.spawn'],
       'docs.signed':      ['document.verify'],   // new scope
       'workflow_step':    ['workflow.transition'], // privileged
     },
   };
   ```
2. **Transition-time check.** `transition()` examines the keys in `delta`, looks up their required scopes, and rejects the write if the *actor* agent's identity does not hold all required scopes. The check is fail-closed: unknown keys are rejected, not silently allowed.

**Implementation sketch:**
```typescript
// src/workflow-state.ts (proposed addition)
import { getIdentity } from './identity/index.js';

function checkKeyAcl(
  workflowType: string,
  delta: Record<string, unknown>,
  actorAgentId: string,
): { ok: true } | { ok: false; reason: string } {
  const acl = workflowKeyAcls[workflowType];
  if (!acl) return { ok: false, reason: 'unknown_workflow_type' };

  const identity = getIdentity(actorAgentId);
  if (!identity) return { ok: false, reason: 'unknown_actor' };

  for (const key of Object.keys(delta)) {
    const required = acl[key];
    if (!required) return { ok: false, reason: `unknown_key:${key}` };
    const missing = required.filter((s) => !identity.scopes.includes(s));
    if (missing.length) {
      return { ok: false, reason: `missing_scope:${missing.join(',')}` };
    }
  }
  return { ok: true };
}
```

Every rejected transition writes an `EvidenceRecord` with `action_type: 'destructive_op'` and `outcome.success: false` so attempted forgeries are auditable.

**Security properties:**
- A sub-agent without `document.verify` scope cannot write `docs.signed`, even if a hallucination tries.
- Privileged step transitions (`workflow_step` key) require `workflow.transition`, which is granted only to orchestrator-class agents.
- Closed-world ACL: unknown keys cannot be written. Workflow types must declare their schema up front.

**Trade-offs:**
- Adds a registration step for every new workflow type. Mitigated by colocating the ACL with the workflow definition module.
- Refactoring an existing workflow's key schema requires a migration. Acceptable cost given the security gain.
- Does not prevent a high-scope agent from writing wrong values into keys it owns — that is a correctness problem, not an authorization one, and is handled by the existing `judge-system.ts`.

### Enhancement 3: Verifiable Delegation Chains for Sub-Agent Spawns

**Problem:** Gap 3 (mostly closed) and a latent issue in NanoClaw — when a parent agent spawns a sub-agent via `agent.spawn`, the resulting sub-identity has an `issuer` field but no signed delegation record proving the parent actually authorized the spawn with the granted scopes.

**ADK pattern:** Sub-agents are class instances. No identity material. The `sub_agents` list is the only authorization signal.

**Proposed solution:** On `createIdentity()` for any non-root agent, the parent agent signs a `DelegationLink` containing `{delegator_id, delegate_id, scopes, issued_at, expires_at}`. The link is stored alongside the sub-identity and verified on every authorization check via a chain walk from the agent up to a root issuer (`nanoclaw-root`).

The delegation verifier enforces *scope narrowing*: each hop's scopes must be a subset of the previous hop's. This is the same property ADK lacks and we already specced in `AGENT_IDENTITY_TRUST_ARCHITECTURE.md` §3.2; this enhancement is the wiring to make it real.

**Implementation sketch:**
```typescript
// src/identity/delegation.ts (new)
export interface DelegationLink {
  delegator_id: string;
  delegate_id: string;
  scopes: AgentScope[];
  issued_at: string;
  expires_at: string;
  signature: string; // delegator signs canonical(link without signature)
}

export async function recordDelegation(
  parentId: string,
  childId: string,
  scopes: AgentScope[],
  ttlSeconds: number,
): Promise<DelegationLink> { /* ... */ }

export async function verifyDelegationChain(
  agentId: string,
): Promise<{ valid: boolean; chain: DelegationLink[]; failureReason?: string }> {
  // Walk from agentId up to 'nanoclaw-root', verifying:
  //  - each link's signature against the delegator's stored public key
  //  - scopes ⊆ previous link's scopes (narrowing only)
  //  - no link expired
  //  - chain terminates at 'nanoclaw-root'
}
```

`authorizeAction()` in `trust-scoring.ts` adds a `delegation_valid` check to the existing `VerificationChecks`. The check is enforced fail-closed only for delegated authority — root-issued identities (issuer === `nanoclaw-root`) skip the chain walk.

**Security properties:**
- Substitution attack on a sub-agent registry detected: a swapped sub-identity has no valid delegation from the parent.
- Scope escalation across hops impossible: chain verification fails on widening.
- `TrustFactors.delegation_depth` already penalizes deep chains — this enhancement makes the depth count real instead of advisory.

**Trade-offs:**
- One extra signature per agent spawn. Ed25519 is fast; cost is negligible.
- Adds a `delegation_links` table; same migration story as the workflow-state tables.
- Requires the parent agent to be loaded with secret-key access at spawn time. `agent.spawn` is already gated on holding the parent's signing key, so no new exposure.

### Enhancement 4: Key Rotation and a Revocation List

**Problem:** Gap 6 — `expireIdentity()` exists but there is no `rotateIdentity()` and no fast-path revocation list. Key compromise response today requires expiring the identity and re-issuing under a new `agent_id`, which breaks every evidence chain pointer.

**ADK pattern:** N/A — no credentials.

**Proposed solution:** Two tightly-scoped additions.

1. **`rotateIdentity(agentId)`** — mints a new Ed25519 keypair, writes a `KeyRotation` record signed by the *old* key (proving the rotation was authorized), and atomically updates the public key. Evidence chain semantics unchanged: records signed under the old key remain verifiable forever because we keep historical public keys in `identity_key_history`.
2. **`revocation_list` table** — `(agent_id, reason, revoked_at, revoked_by_agent_id)`. `verifyMessage()` and `authorizeAction()` consult this list as a first-pass fail-closed check. Adding a row is the fastest compromise response: no code change, no redeploy, takes effect on the next verification.

**Implementation sketch:**
```typescript
// src/identity/lifecycle.ts (new)
export async function rotateIdentity(agentId: string): Promise<{
  new_public_key: string;
  rotation_record_id: string;
}> {
  const oldKey = await loadSecretKey(agentId);
  if (!oldKey) throw new Error('cannot rotate: secret key missing');

  const { publicKey: newPub, privateKey: newPriv } = generateKeypair();

  const rotation = {
    agent_id: agentId,
    old_public_key: (await getIdentity(agentId))!.public_key,
    new_public_key: publicKeyToBase64(newPub),
    rotated_at: new Date().toISOString(),
  };
  const signature = signData(canonicalJson(rotation), oldKey);

  await db.transaction(() => {
    insertKeyHistoryRow(rotation, signature);
    updateIdentityPublicKey(agentId, rotation.new_public_key, newPriv);
  });

  return { new_public_key: rotation.new_public_key, rotation_record_id: signature };
}

export async function revokeIdentity(
  agentId: string,
  reason: string,
  revokedBy: string,
): Promise<void> { /* insert revocation_list row + emit evidence */ }
```

**Security properties:**
- Rotation is authenticated by the old key — only the legitimate holder (or an attacker with the same access) can rotate. Combined with rapid revocation, the attacker's window is bounded.
- Revocation is single-row insert; no rebuild, no redeploy. The cache invalidation hook in `trust-scoring.ts` clears the trust cache for the agent on insert.
- Historical evidence remains verifiable forever because old public keys persist in `identity_key_history` — solves the "break the chain on rotation" problem.

**Trade-offs:**
- A second public key per rotation; storage cost trivial.
- `revocation_list` check on every verification adds one indexed lookup. Measured separately, but expected to be sub-millisecond; we will benchmark before claiming a number.
- If the root key is compromised, this system cannot save itself — root key handling is out of scope and remains a HSM/operations problem.

### Enhancement 5: State-Transition Attribution in the Evidence Chain

**Problem:** Gap 5 (mostly closed) and a latent issue: today `EvidenceRecord.action_type` does not include workflow transitions, so a paused-then-resumed workflow's audit trail will not show the step changes alongside the actions taken.

**Proposed solution:** Add `workflow_transitioned` to the `ActionType` union and emit an evidence record on every `workflow_transition()` call. The record's `action_details` carries `{workflow_id, from_step, to_step, delta_keys}` (key names only — values may be sensitive and live in `workflow_states.state_blob`). The transition is therefore linked to the actor's evidence chain by the same `prev_record_hash` mechanism that protects every other action.

**Implementation sketch:**
```typescript
// inside workflow-state.ts after a successful transition
await createEvidence(
  req.actor_agent_id,
  'workflow_transitioned',
  {
    workflow_id: req.workflow_id,
    from_step: req.from_step,
    to_step: req.to_step,
    delta_keys: Object.keys(req.delta),
  },
  `transition ${req.from_step} → ${req.to_step}`,
  { success: true },
);
```

**Security properties:**
- Replay of a transition cannot fake history — the resulting evidence record's hash chain would not match.
- Disputes over "which agent advanced the workflow past payment_pending" become a single chain query.
- Combines with Enhancement 2 — a denied transition emits a `success: false` record, so attempted forgeries are first-class audit events.

**Trade-offs:**
- One extra evidence row per transition. Storage and signing cost negligible relative to the model call that produced the transition.
- `delta_keys` only — full delta values not in the evidence chain. The full delta lives in `workflow_transitions.delta` (per `IDENTITY_GRAPH_PROPOSAL.md` §3.1), so the audit story is "evidence chain proves *that* the transition happened by this agent; workflow_transitions table holds *what* the transition was." Two tables, joined by `workflow_id + timestamp + actor_agent_id`.

## 5. Sequencing Recommendation

Enhancements 2, 3, and 5 are blockers for safely landing the `workflow_state` machine. They should ship in the same PR or sequence as Phases 1–4 in `IDENTITY_GRAPH_PROPOSAL.md`:

- Phase 1 (Foundations) **must** include Enhancement 2 (scope-tagged keys) and Enhancement 5 (transition attribution). Shipping `workflow_transition` without them re-imports ADK's gaps into NanoClaw.
- Phase 3 (Pause/Resume) **must** include Enhancement 1 (signed webhook resume) before any external integration is wired up. The HMAC fallback in `IDENTITY_GRAPH_PROPOSAL.md` §3.5 is acceptable only for partners that explicitly hold a registered identity.
- Phase 4 (Team Orchestrator Migration) **should** include Enhancement 3 (delegation chains). Today `agent.spawn` creates child identities with `issuer` but no signed link; deferring the chain wiring leaves a latent substitution risk.

Enhancement 4 (rotation + revocation list) is independent of the workflow-state work and can ship on its own timeline. It is currently the most likely single point of failure: if a long-lived agent key leaks, the only response today is `expireIdentity()` plus a re-issue under a new `agent_id`, which breaks downstream references.

## 6. What This Doesn't Solve

- **Root key compromise.** All five enhancements assume `nanoclaw-root` is held securely. If the root key leaks, the entire delegation tree is suspect. Mitigation lives outside this document (HSM, hardware key, offline signing for root issuance).
- **Model-level forgery within an agent's own scope.** If `finance_agent` holds `finance.approved` write scope and its underlying model hallucinates approval, the system records the action as authorized — the failure is in *correctness*, not *authorization*. `judge-system.ts` and outcome verification in `trust-scoring.ts` handle this orthogonally.
- **Side-channel attacks on stored secret keys.** `identity-store.ts` AES-GCM encrypts private keys at rest; OS-level protections beyond that are out of scope.
- **Cross-org trust.** The delegation chain terminates at a single root. Federation across two NanoClaw deployments (or NanoClaw ↔ ADK) is a separate design problem and is not in scope here.
